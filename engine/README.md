# 证据引擎

这是众口里唯一能跑的部分。它把「有多少人在抱怨这一维」从模型的一句自述变成一段可执行的计算。

## 为什么需要它

众口原来的做法是让模型自己读评论、自己数。问题是模型数不准：同一份数据问两次，两次给的条数不一样，而且两个数看起来都挺合理。读者没法判断该信哪个。

这个引擎把可量化的部分固定下来。什么词算提到某一维、这句话是正还是负、有多确定、按什么排优先级，全部写成代码。同一个输入任何时候都得到同一个结论。不需要相信谁，跑一遍就知道。

## 分工

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 读懂反讽、方言、上下文 | 模型 | 规则写不过来，得靠语义理解 |
| 写解释、给改进动作 | 模型 | 需要行业常识和门店经验 |
| 切分句、定位维度、判极性 | 引擎 | 数不准就没法开会，必须可复算 |
| 定置信度 | 引擎 | 不确定到什么程度，必须有一致的尺度 |
| 排序与阈值比较 | 引擎 | 阈值必须固定，否则同一份数据两次结论不同 |
| 出取证单与口径说明 | 引擎 | 格式稳定，未取证项会被强制列出 |

两者冲突时以引擎的计数为准，模型必须解释差异，不能悄悄改数。

## 快速开始

不需要安装任何依赖，标准库即可。Python 3.10 以上。

```bash
cd engine
python -m zhongkou diagnose --split test --top 8       # 18 维短板
python -m zhongkou claim "环境安静，适合聊天"            # 卖点取证
python -m zhongkou quote --dim Ambience#Noise --limit 3 # 取原话
python -m zhongkou audit --split test                  # 与人工标注比对
python -m zhongkou diagnose --csv 本店评论.csv --top 8   # 用自己的数据
```

跑测试：

```bash
python -m unittest discover -s tests -v
```

## 两种排序口径

同一份数据，两种排法，结论会不一样。这是引擎里最容易被忽略、也最容易被评委追问的一处。

| 口径 | 分母 | 回答的问题 | 价位 | 等位 |
|---|---|---|---|---|
| 每百条抱怨数（默认） | 全部评论 | 有多少顾客带着这个不满离开 | 14.0，第 1 | 5.7，第 4 |
| 负向率 | 提到该维的人 | 提到这件事的人里，多少在骂 | 41.1% | 61.6%，第 1 |

负向率高的维度，往往提及量小。只看负向率会去修一个没人感知的问题。默认按每百条排，负向率作为第二列参考。

## 判定规则

### 置信度

| 值 | 条件 | 怎么用 |
|---|---|---|
| 2 高 | 线索词贴着维度词，中间没有转折 | 可以下结论，计入统计 |
| 1 中 | 线索在同一分句但隔得远，或正负线索各一 | 可以说，但要标「方向待核」 |
| 0 低 | 看到了维度词，但线索在别的分句或前后矛盾 | 不下结论，**不计入任何统计** |

置信度 0 的判定不是丢弃，是留白。这一条决定了引擎的准确率只有 0.729，却仍然可以拿来做复核——它不猜。

### 卖点取证

| 结论 | 条件 |
|---|---|
| 违规 | 命中《广告法》第九条绝对化用语，或承诺功效与收益 |
| 有据 | 正面证据 ≥30 条，且正面占比 ≥80% |
| 无据 | 正面占比 <60%，说明有大量反证 |
| 证据不足 | 提及 <30 条，或占比落在 60%–80% 之间 |
| 无法归位 | 这句话落不到 18 维的任何一维，说明它本身不可证 |

三个阈值写在 `claims.py` 顶部，改一处即可全链路生效，不藏在提示词里。

## 和模型版结论的差异

卖点取证那张单子上，引擎把「环境安静」判成有据 93.3%，因为「环境」两字先命中了装修维度。落到噪音维度复算只有 46.7%。

这个差异不是缺陷，是设计。规则层按词面匹配，模型层会结合上下文；两者不一致的地方，正是需要人复核的地方。答辩时如果被问到「你怎么保证结论一致」，可以指着这里说：不一致本身就是输出的一部分。

## 三条实现原则

**缺失不补。** 一维只有 12 条提及，就写「样本不足」，不用行业经验替它补一个结论。看起来完整，实际上是无中生有。

**中性留白。** 「一般」「还行」「没惊喜」记为中性，不掰成差评，也不当好评。这类顾客最难改，也最容易被统计口径抹掉。

**阈值显式声明。** 30 条、80%、60% 这些数写在代码顶部，不散落在逻辑里。评委可以改一个数，看结论怎么跟着变。

## 接入智能体

三种方式，按平台支持情况选：

1. 代码解释器直接跑。智能体把用户上传的评论表存成 CSV，调用 `python -m zhongkou diagnose --csv case.csv --json`，拿回结构化结果再组织语言。
2. 注册为工具。把 `diagnose` 和 `claim` 各暴露成一个工具，输入是 CSV 路径或一句话，输出是统计表。
3. 离线复核。模型先出报告，再用引擎跑一遍，对比两者的维度排序与条数，差异项单独列出。

第 3 种最省事，也最能体现「引擎不复核模型，模型反过来复核它」。

## 已知局限

- 极性准确率 0.729。反讽（「真是太好了，等了两个小时」）会判成正向
- 维度 F1 0.725，会漏判。漏判的维度只能写「未形成判定」
- 「环境」这类复合词会落错维度，引擎没有自纠能力
- 评论里的「排队」可能指等位，也可能指等上菜，混在一起时偏向等位
- 不做分词模型，靠词表与子句规则，新词（网络用语、方言）需要补词表
- 输入只吃 CSV，不做 PDF、图片、外卖平台接口
